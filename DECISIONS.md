# Phase 0 decisions

Settled 2026-09-19. These are closed. Reopen only with a written reason.

## 1. Encryption scope

TLS in transit, plus application-level encryption at rest.

- Message bodies are encrypted in the application before they reach MySQL, using a
  symmetric key loaded from `ENCRYPTION_KEY` in the environment.
- Questionnaire answers containing free text are treated the same way.
- Photos are stored in private storage (no public bucket, no guessable URL). Served
  through an authorised backend route, never a direct link.
- Not end to end. The server can read messages, which is required because the admin
  dashboard and the email notifications both need plaintext.

Threat model this covers: a stolen database dump or backup. Does not cover: a
compromised running server, since the key is in its environment.

## 2. Email address source

A required field on the questionnaire. The user types it.

- No external lookup, no dependency on any other system.
- A typo means the rejoin link is undeliverable. Mitigation: show the address back to
  the user on the confirmation screen and on the chat page, so the mistake is visible
  while the original link still works in that browser tab.

## 3. Admin scoping

Every admin can see every Station and every Request.

Reasoning: admins work the queue together, so partitioning access would get in the way.
Stations are an organisational grouping, not a permission boundary.

Implementation note: keep `admins.station_id` in the schema as a nullable column meaning
"home station" (used for default filter and for routing, not for access control). This
costs nothing now and leaves room if scoping is ever needed. Access control code must
not read it.

## 4. Questionnaire structure

Fixed fields for now, dynamic-ready storage.

- The intake form is hardcoded: number field, text field, photo upload, plus email.
- Answers are still stored as key/value rows in `questionnaire_answers`, not as columns.
- Adding per-Station configurable fields later means adding a definition table and a
  renderer, with no migration of existing answer data.

## 5. Frontend frameworks

- Widget: plain TypeScript, no framework, mounted into a Shadow DOM so the host page's
  CSS cannot reach it and its own CSS cannot leak out. Built to a single JS file.
- Admin dashboard: React with Vite. Bundle size is not a constraint there.

They are separate codebases. They share nothing except the HTTP and WebSocket contract.

# Phase 2 decisions: schema conventions

Settled 2026-09-19. These apply to every table. Each is expensive to change once real
data exists.

## 6. External ID format

The External ID is typed by the user into the questionnaire. Exactly two shapes are
valid:

    ^[A-Z]{2}[0-9]{4}$     e.g. JX1234
    ^[0-9]{8}$             e.g. 12345678

Rules:

- Validation is strict. Anything matching neither pattern is rejected at the form and
  at the rejoin endpoint, before any database query runs. This also makes ID spraying
  cheap to defend against, since malformed guesses cost nothing.
- Letters are always stored uppercase. Input is normalised with `.strip().upper()`
  before validation, so `jx1234` becomes `JX1234`. A user typing lowercase on a phone
  keyboard still finds their request.
- Normalise in exactly one place: a validator on the Pydantic schema. Never
  re-normalise in routes or services, or the two copies will drift.
- Still NOT unique. One person can open several requests under the same External ID.
  It identifies a person, not a chat, and it is not an access key.

Column: `VARCHAR(16)`, indexed, not unique. 16 rather than 8 leaves room if a third
format ever appears.

## 7. Primary keys

`requests.id` is `BINARY(16)` holding a UUID, wrapped in a custom SQLAlchemy type so
Python code only ever sees `uuid.UUID`.

- Reason: 16 bytes rather than 36, repeated in every foreign key and index entry.
- Generate with UUIDv7 (`uuid.uuid7()`, available in Python 3.14), not UUIDv4. v7 is
  time ordered, so inserts append to the index instead of fragmenting it.
- Cost accepted: raw SQL in Workbench shows binary, so manual queries need HEX() and
  UNHEX().

Every other table uses `BIGINT` auto-increment. Only `requests.id` is referenced from
outside the system.

## 8. Timestamps

- Store UTC everywhere. MySQL `DATETIME` carries no timezone, so a local time cannot
  be interpreted later. Convert to local time in the browser, never in the database.
- `created_at` is generated by the database: `server_default=func.now()`. Two app
  instances with skewed clocks must not produce inconsistent ordering, and a row
  inserted by raw SQL must still get a timestamp.
- `expires_at` is computed in Python, from `REQUEST_EXPIRY_DAYS` in config. The
  database has no business knowing the application's configuration.

## 9. Enums

Do not use MySQL's native `ENUM` column type.

- Adding a value to a native ENUM requires an ALTER TABLE that rewrites the table.
- Instead: a short `VARCHAR` column plus a Python `enum.StrEnum`, validated by
  SQLAlchemy on write.
- Result: the database stores a readable string, the application owns the valid set,
  and adding a value is a code change rather than a migration.

Applies to `messages.sender_type` (user | admin) and `requests.status`.

## 10. Cascade deletes do not delete files

Foreign keys use `ON DELETE CASCADE`, so deleting a `requests` row removes its
messages, questionnaire answers and attachments.

Photos are NOT in the database. Deleting an `attachments` row removes the only record
of where the file is, leaving the file orphaned on disk or in the bucket with nothing
pointing at it.

Therefore the Phase 8 cleanup job MUST run in this order:

    1. read the attachment rows for the expiring request
    2. delete those files from storage
    3. delete the request row (cascade removes the rest)

Never the reverse. Deleting rows first makes the file list unrecoverable and those
bytes permanently unreachable.

# Revision, 2026-09-19: real domain and scope

The project is a radiology study-request consult chat for a hospital. The earlier
generic wording is superseded where it conflicts.

## 11. Scope boundary

The other party owns the questionnaire form, the cascading Modality > Body region >
Study dropdowns, and the station sorting. They will pull this repo and integrate it.

This repo owns:

- an intake API that accepts an already-sorted request
- the temporary chat (user side and admin side)
- the unread reply notification email
- the 7-day expiry and cleanup

This repo does NOT own: the form UI, the study taxonomy, the sorting rules. Do not
reimplement them. The station arrives as a value in the intake payload.

Consequence: treat the intake endpoint as a public API contract. It gets versioned,
documented and validated defensively, because a caller we do not control depends on it.

## 12. The data is patient data

The payload carries patient name, HN, sex, age, clinical history and a photo of a pink
slip bearing an HN sticker. This is identifiable medical information. It raises three
earlier decisions from preference to requirement:

- Application-level encryption at rest now covers questionnaire answers and message
  bodies. Photos go to private storage, never a public bucket or guessable URL.
- Emails contain a link and nothing else. No patient name, no HN, no history, no
  study type in the subject or body. Hospital mail is forwarded and archived outside
  this system's control.
- The 7-day delete is a retention policy, not housekeeping. It must be reliable and it
  must remove files as well as rows (see section 10).

Also: do not log payload contents. Log request IDs and station names only. An
application log is the easiest place to leak this data by accident.

## 13. Questionnaire fields

Fixed set, supplied by the caller. Stored as key/value rows in
`questionnaire_answers` per decision 4, except the fields promoted to columns.

    patient_name        required
    sex                 required     male | female | other
    age_value           required     integer
    age_unit            required     years | months | days
    hn                  required     the External ID (see section 6)
    qshc_hn             optional     second hospital number
    modality            required     CT | MRI | U/S | Fluoroscopy
    body_region         required     free text, caller's taxonomy
    study               required     free text, caller's taxonomy
    time_period         required     today | 1d | 2d | 3d | 1w | 2w | 1m | 2m | 3m | 6m | specific
    specific_date       optional     required when time_period is specific
    patient_history     required     long free text
    pink_slip_photo     required     image, Phase 6
    md_name             required     requesting doctor
    staff_name          required     supervising staff
    tel                 required     callback number
    consultee_email     required     where the reply notification goes

Promoted to columns on `requests`: hn (as external_id), consultee_email (as email),
station_id. Everything else is an answer row.

Ages: store value and unit separately. Do not normalise to years. A 7-day-old neonate
and a 7-year-old are different patients and the resident must see which.

## 14. Email behaviour, revised

Supersedes the confirmation email in the original sketch.

- NO email is sent when a request is created. The doctor goes straight into the chat
  from their browser after submitting.
- The ONLY email is the unread reply notification: when a message has been unread for
  5 minutes, email the consultee a link to the chat.
- Recipient is the consultee (the M.D. who submitted). The resident answers from the
  admin dashboard and is not emailed.
- UNREAD_EMAIL_DELAY_MINUTES = 5.

Consequence to be aware of: with no email at submit, a doctor who closes the tab before
any reply arrives has no link. Their route back in is the HN rejoin flow, which emails
the link on request. That flow is therefore load-bearing, not a convenience.

## 15. Consultee identity comes from SSO, never from the payload

The host application authenticates the requesting doctor through SSO. This
system takes the doctor's email from that server-side session.

There is deliberately no email field in the intake payload. An email in a
request body is client-supplied, so anyone able to reach the endpoint could
create a consult naming someone else's address, and this system would then
email that person a link to patient data.

Integration point: `app/core/identity.py`. Replace `get_current_consultee`
with a dependency that reads the host application's session and returns a
`Consultee`. Nothing else in the codebase changes.

The shipped implementation is a development stub that reads `X-Consultee-Email`
and `X-Consultee-Name` headers, and only when `DEV_AUTH_STUB=true`. With the
flag off, the default, it returns 500 rather than falling open. An
unimplemented auth dependency that quietly returns a default identity is worse
than one that errors, because nothing looks broken.
